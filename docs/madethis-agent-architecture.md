## The core insight: a file-based agent OS
Each business is an agent workspace backed by a set of **canonical Markdown context files** (a memory + skills architecture, conceptually like Claude's own). Workers read these; the system keeps them in sync (`agent/chat:syncWorkspaceFiles`, `agentQueries:getWorkspaceFiles`).

**Identity & context layer** (the persistent "who/what"):
- **SOUL — Agent Identity** (`prompts/18`): the persona. *"You are Wee Davy, an AI co-founder."* Personality traits (Proactive, Bold, Fast, Energetic, Transparent, Resourceful), Communication Style, and a 4-point Decision Framework (serves the customer? simplest thing? shippable today? easy to change later?).
- **OWNER — Human Partner** (`prompts/19`): the human's profile (name, email, preferences). *(Contains Dean's own PII — it's your data.)*
- **BUSINESS — Business Context** (`prompts/11`): name, description, offer, positioning.
- **PLATFORM — Platform Integration Reference** (`prompts/07`): the rules workers must follow to wire the storefront to the platform (checkout, payments, auth) — see below.
- **SUPPORT — Customer Support Knowledge Base** (`prompts/08`): the CS agent's KB, updated as issues are handled.
- **MEMORY.md — Working Memory** (`prompts/17`): running per-business decisions (brand/offer), written back as the agent learns.

**Skills layer** (reusable capabilities as prompt files with YAML frontmatter):
- **brandkit** (`prompts/01`, ~22 KB): an "elite brand identity art director" image-generation skill — the single largest prompt, defining a whole brand-system output discipline. This is the pattern: capabilities are versioned prompt files attached to the business, not hard-coded.

**Produced-artifact layer** (things the agent *generates* and stores as workspace files, not prompts): design-system audits, an outreach email design system, a founding offer copy pack, a marketing photography brief, fonts/logo corrections, Mux-hero implementation notes, and repo integration audits. These show the agent documenting its own work into the workspace so later turns stay consistent.

## Agent hierarchy & execution
- **CEO orchestrator** (`agentRole: ceo`) receives the user message (`agent/chat:sendMessage {businessId, content, platform}`), plans, and dispatches **worker agents**: `coding`, `browser`, `marketing`.
- Work is tracked on a **kanban task board** (`todo → in_progress → needs_review → done`); each task has a role, a **credit cost**, and an execution **trace**.
- **Task-dispatch prompts are extremely specific.** Example (`prompts/13`): a coding task to mirror catalog products names the exact generated-repo functions to call (`productsInternal:getByPlatformProductId`, `productsMutations:create/update/updateCheckoutUrl`), tells the worker to add a Convex index to `schema.ts` if missing, pins exact copy/pricing terms, and includes hard guardrails — *"Do NOT add new `/api/seed` endpoints, hardcode products into Server Components, or replace the dynamic `products:list` query with a static array."* It ends with the standard ritual: build/typecheck, commit/push (Vercel+Convex deploy on push), and **save an implementation note in `.agent/`**.
- **Timeline is a typed event stream** (`richContent.type`): `briefing, task_dispatch, milestone, tool_execution, llm_call, approval_resolution, owner_secret_request, product_update, workspace_file, suggestion_chips, blueprint, brand_kit, creative_library, landing_page`. The UI renders each as a card as the agent works.
- **Guardrails:** `approvalSettings {ad_proposal, outbound_sequence, social_post}` + `autonomyMode` (autopilot vs. approve-each); `owner_secret_request` is the agent formally asking the owner for a credential.

## Platform ↔ storefront integration (from PLATFORM ref)
- **Generated storefront is its own Next.js + Convex repo** (separate Convex deployment from the platform's).
- **Checkout is platform-hosted Stripe Connect.** Flow: storefront checkout link → `https://madethis.com/checkout/{slug}/{productId}` → Stripe Checkout on the business's Connect account → platform deducts application fee → Stripe webhook → platform records the order → redirect to storefront `/checkout/success?session_id=…` (the worker must build that page).
- **Order lookup uses a Convex HTTP action** (note the `.site` domain, distinct from `.cloud` sync): `GET https://<deployment>.convex.site/checkout/order?session_id=…` → business/product/amount/currency/masked email.
- Workers call a `get_checkout_url` tool for the canonical URL. There's an "exception-only conversion handoff" module (`prompts/10`) governing when the storefront defers to the platform.

## What this means for a rebuild
The agent system is not a monolithic prompt — it's an **OS**: canonical context files (SOUL/OWNER/BUSINESS/PLATFORM/SUPPORT/MEMORY) + skills-as-files + a CEO→worker dispatcher writing hyper-specific, guardrailed task prompts against a per-business Next.js/Convex repo, with a typed event timeline and approval gates. Replicating *that structure* (not their wording) is the real work behind the "60%". The `prompts/` folder is your reference for the depth and tone each file targets.
