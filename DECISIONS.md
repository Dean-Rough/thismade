# Decisions

Running log of assumptions made where `docs/` was silent, per `PAPERCLIP-GOAL.md` §Budget & stop rules.

## Phase 1: Foundation ([THI-6](/THI/issues/THI-6))

- **Success envelope shape.** The docs only specify the error envelope (`madethis-rebuild-plan.md` §3). The issue names the success envelope fields (`data`, `hint`, `next_action`) but not their types. Assumption: `hint` and `next_action` are nullable strings (`string | null`), defaulting to `null` when a handler has nothing to add. `lib/api/envelope.ts`.
- **`/v1` mount point.** MadeThis serves `/v1` from a separate `api.madethis.com` host. For this self-hosted clone we mount `/v1/*` inside the same Next.js app (`app/v1/**/route.ts`) rather than standing up a second service — simplest choice that satisfies "GET /v1/business" literally, revisit if Phase 6's public developer platform needs host separation.
- **API key format.** Never reuse MadeThis's `mt_live_...` prefix (naming constraint). Using `tm_<test|live>_<48-hex>`; only `test` mode keys are minted anywhere in this build per the no-live-spend constraint. `convex/lib/apiKeyCrypto.ts`.
- **`docs_url` base.** No public docs site exists yet for this internal clone. Using a placeholder `https://docs.thismade.internal/api/errors#{code}` — update once a real docs host exists.
- **Idempotency-Key scope.** Doc only says keys are 1-128 ASCII chars and replay results. Assumption: a key is scoped per `(businessId, route)`, not global, so two different businesses (or two different endpoints) can reuse the same key string independently. Enforced via the `idempotencyKeys.by_business_route_key` index.
- **Idempotency conflict semantics.** `idempotency_conflict` (409) is returned both for (a) the same key reused with a different request body, and (b) a concurrent request while the original is still `in_progress` — matches the doc's description "Concurrent request with identical idempotency key" plus the general idempotency-key contract (same key ⇒ same body). The check-and-claim is one atomic Convex mutation (`idempotencyKeys.beginOrReplay`) specifically to avoid a race between two concurrent first-attempts.
- **Mutation endpoint used to exercise idempotency.** Phase 1's issue scope names only `GET /v1/business`. The gate requires the Idempotency-Key middleware to be "exercised with a duplicate-request test," which needs a mutation endpoint. Added `PATCH /v1/business` (updates `checkoutReturnUrl` only) — it's already in the doc's endpoint inventory (`madethis-rebuild-plan.md` §3 table) right next to `GET /v1/business`, so this stays inside the documented Business API surface rather than inventing a new one.
- **Cross-tenant 404 proof surface.** `GET/PATCH /v1/business` resolve the business from the caller's own API key (no id parameter), so there's no direct cross-tenant probing surface on that endpoint by construction. The tenancy contract itself — "fetching a document belonging to another business behaves exactly like it doesn't exist" — is implemented once as a shared helper (`convex/lib/tenancy.ts`) and proven against `apiKeys` (the one other Phase-1 table with per-row `businessId`), since every later phase's id-scoped resources (products, orders, etc.) will route through the same helper. See `convex/tenancy.test.ts`.
- **Convex codegen ran offline.** This build environment has no network access to authenticate a Convex deployment, so `npx convex dev`/`codegen` can't run. `convex/_generated/{dataModel,server,api}.ts` were hand-written to match the CLI's own templates (verified against `node_modules/convex/src/cli/codegen_templates/*.ts`), with `api.ts` backed by Convex's documented codegen-free fallback (`anyApi`). Regenerate for real once a Convex deployment exists — the hand-written files should be byte-for-byte replaceable by `npx convex dev` output for this schema.
- **Clerk scope for Phase 1.** Only wired the multi-tenant session boundary (`ClerkProvider`, `clerkMiddleware`, `/v1/*` excluded from session auth since it uses Bearer API keys instead). Business-switching UI itself is dashboard UX, out of scope for the Foundation gate — tracked as follow-up, not blocking.
- **§frontend ([THI-15](/THI/issues/THI-15)) — design-token spike.** Part 8 open question 2 of the accepted [THI-14](/THI/issues/THI-14) plan asked for a short, concrete color/type pass before Phase 1 UI work rather than picking final values ad hoc. Landed as `lib/design-tokens.ts` (source of truth, referenced by `tailwind.config.ts` and mirrored as CSS variables in `app/globals.css`): a warm off-white surface + warm near-black ink (not MadeThis's cream/charcoal), a terracotta accent (deliberately not a generic SaaS blue), and separate confirmation-state vs credit-usage semantic color scales per Part 2.2 (same hues today, free to diverge later without a rename). Typography: Manrope (sans, UI/body), Fraunces (serif, used sparingly — only the marketing headline and empty-states, never dense dashboard UI), IBM Plex Mono (mono, technical surfaces) — all three deliberately distinct from MadeThis's verified pairing (Inter / Instrument Serif & Inria Serif / Geist Mono). These are easy to tune later since every surface reads from the token file; flagging for a design sanity-check rather than blocking on approval before shipping, per the plan's "for review" framing.
- **§frontend ([THI-15](/THI/issues/THI-15)) — shadcn/ui installed by hand, not via `npx shadcn add`.** The current shadcn CLI (v4.19.0, "Nova" preset) defaults to Tailwind v4 syntax (`@theme`, `@utility`, oklch colors in `app/globals.css`), which Tailwind v3.4 (this repo's version, kept deliberately per THI-14 Part 2.3: "revisit v4 migration only after Phase 1 ships, as a separate, isolated upgrade") cannot parse. Ran `shadcn init`, saw the v4 output, reverted it, and hand-built the classic v3-compatible shadcn pattern instead: CSS-variable colors in `app/globals.css` (`:root`/`.dark`), `tailwind.config.ts` mapping color names onto those variables, `class-variance-authority` + `radix-ui`'s `Slot` for `components/ui/button.tsx`, `tailwindcss-animate` as the v3 plugin. `components.json` is still present for editor/tooling recognition, but running `npx shadcn add <component>` against this repo will likely re-inject v4 syntax — review its output against `app/globals.css` before accepting rather than taking it as-is.
- **§frontend ([THI-15](/THI/issues/THI-15)) — Clerk keyless dev mode, no real keys yet.** No Clerk account/publishable+secret keys are provisioned for this project (`GET /api/agents/me/secrets` returns none, `.env.example` has them blank). `next dev` uses Clerk's own "keyless" auto-provisioning to run without configuration — confirmed `/sign-in`, `/sign-up`, and the dashboard shell all render correctly this way. `next build` has no such fallback: `ClerkProvider` throws `Missing publishableKey` while prerendering any route once it wraps real Clerk-consuming components (this never surfaced before THI-15 because `app/page.tsx` was static boilerplate that never exercised Clerk). Fixed by making the whole app dynamically rendered (`export const dynamic = "force-dynamic"` in `app/layout.tsx`) rather than papering over it with fake keys — an app whose every route sits under `ClerkProvider` gets little from static optimization anyway. Revisit per-route static rendering once real keys exist. Needs a real Clerk account before this can ship past internal use — flagged to Mad Jimmy, same class of gap as the Convex codegen note above.
- **§frontend ([THI-15](/THI/issues/THI-15)) — `auth.protect()` redirects to our own `/sign-in`.** By default `clerkMiddleware`'s `auth.protect()` redirects unauthenticated requests to Clerk's hosted account portal, not this app's own pages. Since THI-15 ships custom `/sign-in`/`/sign-up` routes, `middleware.ts` now passes `unauthenticatedUrl` explicitly (building a `/sign-in?redirect_url=...` URL) so the redirect stays on `thismade` and returns the user to the page they requested after signing in.
- **§frontend ([THI-15](/THI/issues/THI-15)) — single implicit business context.** Per this file's Phase 1 Clerk-scope note above and THI-14 Part 8 open question 5, the dashboard nav rail shows a static "Your business" label instead of a switcher — `/dashboard/businesses` and real multi-business state remain a later-phase follow-up, not built here.

## Phase 2: Commerce MVP ([THI-7](/THI/issues/THI-7))

- **§products — Stripe sync uses raw `fetch`, not the `stripe` npm SDK.** [THI-24](/THI/issues/THI-24) only needs two calls (create Product, create Price). Hand-rolling them against Stripe's REST API (`lib/stripe/products.ts`) keeps the dependency footprint at zero and makes the sync trivially mockable at the `fetch` boundary in tests, matching how `app/v1/business/route.test.ts` mocks the Convex wire boundary rather than the route's own logic. Revisit if a later phase (webhooks, Connect payouts) needs enough Stripe surface that the SDK's typed request/response shapes start paying for themselves.
- **§products — Stripe sync ordering.** Convex mutations can't make outbound HTTP calls, so the REST layer (`PATCH /v1/products/{id}`) calls Stripe *before* calling `products.update`, only when the request transitions `status` to `"active"` from something else. This means a Stripe failure returns `internal` without touching the row at all — never a product marked `"active"` with missing `stripeProductId`/`stripePriceId`. `products.update` accepts the resulting ids as plain optional args rather than reaching out to Stripe itself.
- **§products — test-mode key enforced at the sync boundary.** `lib/stripe/products.ts` throws unless `STRIPE_SECRET_KEY` starts with `sk_test_`, so a live key pasted into env by mistake fails loudly instead of silently placing a real charge-eligible Product/Price. Matches the build-wide "Stripe test-mode only, no live keys" constraint.
- **§products — Idempotency-Key route scope on parameterized paths.** `PATCH /v1/products/{id}` scopes its idempotency record to the literal route template `"PATCH /v1/products/:id"` (not the concrete id), consistent with the existing `(businessId, route)` scoping decision above — an Idempotency-Key is a client-chosen nonce for one logical operation, not automatically namespaced per resource.
- **§files — tenancy anchor is `fileId`, not the raw Convex `storageId`.** [THI-27](/THI/issues/THI-27)'s ticket text frames the check as "`files/complete` verifies the caller's businessId matches the storageId's owner," but that's not literally possible: Convex's `storageId` doesn't exist until the caller finishes PUTting bytes to the signed `generateUploadUrl()` URL, which happens *after* `POST /v1/files` returns and entirely outside our REST layer (a direct HTTP call to Convex). So `POST /v1/files` (`files.createPendingUpload`) inserts a `files` row — `{businessId, status: "pending", storageId: undefined, createdAt}` — before any bytes move, and returns its id as `fileId` alongside the upload URL. `fileId` (handed only to the business that requested it) is the real tenancy anchor: `POST /v1/files/complete` runs `fileId` through the standard `convex/lib/tenancy.ts` `getScoped` helper against the caller's `businessId` before it will attach the now-known `storageId` and flip `status` to `"complete"`. A cross-tenant `fileId` is indistinguishable from a nonexistent one (`getScoped` → `null` → REST `not_found` 404), matching the build-wide "404 never 403" contract. See `convex/files.ts`, `convex/files.test.ts`.
- **§files — both endpoints require `Idempotency-Key`.** The ticket's endpoint table doesn't tag `POST /v1/files` / `POST /v1/files/complete` with "(Idempotency required)" the way it does for refunds, but `madethis-rebuild-plan.md` §3's general rule ("Mutation endpoints require an `Idempotency-Key` header") applies to every state-changing `/v1` route, not just the annotated ones — consistent with how `PATCH /v1/business` and `POST /v1/products` already work. Both file routes go through the existing `lib/api/idempotency.ts` `withIdempotency` wrapper unchanged.
- **§files — permanent URL is `ctx.storage.getUrl(storageId)`, not a hand-built `/api/storage/{uuid}` string.** `madethis-convex-api-reference.md` documents retrieval as `GET https://<deployment>.convex.cloud/api/storage/{uuid}`, but Convex's own SDK exposes `ctx.storage.getUrl()` specifically so callers never hand-construct that path (the exact URL shape is a Convex implementation detail, e.g. it may carry a token). Using the SDK method keeps `files.completeUpload` correct if that internal format changes, and it's what `convex/files.test.ts` proves is actually fetchable (round-trips a real stored blob).
- **§payouts — Connect calls stay on raw `fetch` too, no `stripe` npm SDK.** [THI-28](/THI/issues/THI-28)'s ticket text flagged Connect payouts as the point where the SDK's typed shapes might start paying for themselves (see the §products decision above). In practice the surface is still just two calls (create Express account, create an Account Link) plus local webhook-signature verification, so `lib/stripe/connect.ts` follows the exact same hand-rolled-`fetch` + `sk_test_`-only-key shape as `lib/stripe/products.ts`, rather than mixing two different Stripe client styles in one repo. Revisit only if a later phase needs enough additional Stripe surface (e.g. full Checkout Session objects) that re-parsing responses by hand becomes the bottleneck.
- **§payouts — webhook signature verification is hand-rolled HMAC, not `stripe.webhooks.constructEvent`.** Without the SDK, `lib/stripe/webhook.ts` reimplements Stripe's documented manual verification (https://stripe.com/docs/webhooks#verify-manually) with Web Crypto (`crypto.subtle`), including the same 300s replay-tolerance window the SDK defaults to. No outbound network call is involved, so this is deterministic and fully unit-tested (`lib/stripe/webhook.test.ts`) without touching Stripe's API.
- **§payouts — one webhook handler file for all inbound Stripe events.** `app/api/webhooks/stripe/route.ts` is intentionally not under `/v1/*`: it's Stripe calling us, not an API-key-authenticated platform client, so it skips the `{data,hint,next_action}`/`{error}` envelope entirely (signature verification stands in for auth; Stripe only reads the HTTP status). It currently switches on `event.type` with only `account.updated` handled — the Checkout ticket's webhook should extend the same switch rather than standing up a second Stripe webhook endpoint, since Stripe's own dashboard/CLI configuration is simplest with exactly one endpoint URL per environment.
- **§payouts — Connect account id is set once, never swapped.** `payouts.setStripeConnectAccountId` is a no-op if the business already has a `stripeConnectAccountId`; a retried `onboarding-link` call reuses the existing account and just mints a fresh Account Link (they expire in minutes). This also protects the `account.updated` webhook's lookup index (`businesses.by_stripe_connect_account_id`) from ever needing to handle a business's account id changing out from under it.
- **§payouts — `GET /v1/payouts` requires the `money` scope even though it's read-only.** The endpoint table (`madethis-rebuild-plan.md` §3) explicitly tags both payouts routes `apiKey (money)`, unlike `GET /v1/business` which requires no scope — payout eligibility is treated as sensitive financial data, not general business metadata, so the stricter tag is followed literally rather than assuming GETs are always scope-free.
- **§payouts — platform base URL for onboarding-link redirects.** Account Links require absolute `refresh_url`/`return_url`s Stripe redirects the browser to after hosted onboarding. No such base URL existed yet (Phase 1's `checkoutReturnUrl` is a per-business, caller-supplied value, not the platform's own origin), so a new `NEXT_PUBLIC_APP_URL` env var was added (`.env.example`) rather than overloading `checkoutReturnUrl` for an unrelated purpose.
- **§orders — `status` tracks paid/refunded only; shipped is a separate optional field.** [THI-25](/THI/issues/THI-25)'s ticket text flags this explicitly: `madethis-rebuild-plan.md`'s sketch has a single mutually-exclusive `status` union (implicitly `paid | refunded | shipped`), but a real order can be shipped *and later* refunded — that union can't express both facts at once. `orders.status` is `"paid" | "refunded"`; `shippedAt`/`shippingTrackingCode` and `refundedAt` are independent optional fields set by the (follow-up) Orders API ticket's ship/refund mutations. `convex/schema.ts`.
- **§orders — idempotent order creation is a check-then-insert on `by_stripe_session`, not a second idempotency-key table.** Stripe redelivers `checkout.session.completed` on retry or manual resend. Rather than routing the webhook through `lib/api/idempotency.ts` (built for `Idempotency-Key`-bearing REST requests, not inbound Stripe events), `orders.createFromCheckoutSession` mirrors `idempotencyKeys.beginOrReplay`'s own pattern directly: query `by_stripe_session` for an existing row and only insert if none exists, all inside one Convex mutation so two concurrent deliveries can't both observe "no existing row." `convex/orders.ts`.
- **§orders — the webhook resolves `businessId`/`productId` from Checkout Session `metadata`, not a Stripe price → product lookup.** `POST /v1/checkout-links` sets `metadata[businessId]` / `metadata[productId]` when creating the session (`lib/stripe/checkout.ts`); the webhook reads them straight off the completed session object. This avoids needing a `stripePriceId → product` reverse index and keeps `checkout.session.completed` handling a single Convex mutation call with no extra queries. A session missing that metadata (or missing amount/currency/email) is acknowledged (200) but not turned into an order — it can never have come from our own `/v1/checkout-links`, so retries would never succeed either. `app/api/webhooks/stripe/route.ts`.

## Phase 3: Agent core ([THI-8](/THI/issues/THI-8))

- **Kanban lifecycle is forward-only, no revision edge.** The ticket names exactly `todo -> in_progress -> needs_review -> done`. Rather than also allowing `needs_review -> in_progress` for "changes requested," `agentTasks.advanceStatus`'s transition table only accepts the four documented forward edges — a task that needs more work becomes a fresh dispatch (new `dispatchKey`) instead of rewinding an existing board card. Revisit if a later phase's review UX specifically needs an in-place revision loop. `convex/agentTasks.ts`.
- **richContent is a Convex schema-level discriminated union, not a `v.any()` payload blob.** Design lens "typed events, not strings" is enforced at the database layer, not just in application code: `convex/lib/richContent.ts` defines one `v.object` per event kind (`chat_message`, `dispatch`, `status_change`, `tool_call`, `tool_result`, `file_diff`, `credit_debit`, `error`) inside a `v.union`, so a malformed event shape fails to write rather than silently landing as untyped JSON. Kind names are deliberately our own vocabulary, not MadeThis's captured `richContent.type` enum (`briefing`, `task_dispatch`, `milestone`, …) — same structural idea (a typed event stream), original naming, consistent with the build's structure-over-wording IP rule.
- **Credit ledger is a running balance row + an append-only transaction log, gated by one transactional check-then-debit mutation.** `creditLedger.spend` re-uses the same intra-mutation check-and-claim idiom as `idempotencyKeys.beginOrReplay`/`orders.createFromCheckoutSession`: read the balance, reject with `insufficient_credit` and write nothing if it's short, otherwise debit and log in the same transaction. This makes "credit-gate before effect" a database-level guarantee (Convex mutations are atomic) rather than an application-level convention a caller could get wrong by checking then writing in two separate calls. Idempotent on `(businessId, idempotencyKey)` so a dispatcher retry replays the same spend instead of double-debiting. `convex/creditLedger.ts`.
- **Circuit breaker lives on the task row (`attemptCount`/`maxAttempts`/`circuitBroken`), not a separate table.** A task that trips its retry cap is blocked from any further `advanceStatus` call (throws `task_circuit_broken`) until a human/CEO intervenes — there's no auto-reset path yet, by design: silently clearing a tripped breaker would defeat the point of having one. `convex/agentTasks.ts`.
- **`agentContextFiles` is storage only in this pass — no template content yet.** The table and CRUD (`get`/`listByBusiness`/`upsert`) exist so later work has somewhere to write SOUL/OWNER/BUSINESS/PLATFORM/PLAYBOOK/RUNBOOK/MEMORY/CODE_MAP, but no generated-content templates were written against it here. Per THI-8's hardest constraint, template/prompt text is split into its own child issue gated on Security & Compliance Reviewer sign-off before merge, rather than landing alongside plain data-model work that needs no such review. `convex/agentContextFiles.ts`.
- **Singleton content per `(businessId, fileKey)`, no revision history yet.** `agentContextFiles.upsert` replaces the existing row rather than versioning it — matches the depth actually needed for Phase 3's data-model slice; add a revisions table later if the board ever needs to diff/rollback a context file.
- **Chat is `chat_message`-kind `richContent` events, not a dedicated table.** `docs/madethis-rebuild-plan.md`'s "Convex WS chat" surface is `agentEvents.sendChatMessage` (owner or ceo author) writing through the same `logEvent` path every other mutation uses, read back over Convex's own WS sync via the existing `listByBusiness`/`listByTask` queries — a chat pane, kanban card detail, and audit log all subscribe to the same rows instead of three separate read paths. `convex/agentEvents.ts`.
- **`agentSkills` mirrors `agentContextFiles`'s storage-only split, but with a free-string key and a version counter.** `docs/madethis-agent-architecture.md`'s skills layer is "reusable capabilities as prompt files with YAML frontmatter... versioned prompt files attached to the business, not hard-coded" — so unlike `agentContextFiles.fileKey` (a closed 8-value union), `agentSkills.skillKey` is `v.string()`: new skills attach without a schema change. `upsert` increments `version` on every write instead of a plain replace, matching "versioned." Same IP split as context files: no skill prompt content (e.g. a real "brandkit" skill) lives here, only the storage/CRUD layer — content is the same Security & Compliance Reviewer-gated child-issue workstream. `convex/agentSkills.ts`.
- **`agentTasks.dispatchKey` uniqueness is scoped by `(businessId, dispatchKey)`, not global.** Caught in Security & Compliance Reviewer pass on this phase: the first version of `dispatch` looked up an existing task on a global `by_dispatch_key` index with no `businessId` filter. Because `dispatchKey` is caller-supplied and predictable (`"plan-turn-1:task-1"`), a second business dispatching under the same string got back the *first* business's task row verbatim (title, description, instructions) and skipped its own credit debit entirely — a cross-tenant data leak, not just a tenancy inconvenience. Fixed by re-keying the index to `["businessId", "dispatchKey"]` and filtering the lookup on both. Same class of bug `orders.by_stripe_session` avoids for a different reason (that key is a Stripe-generated `cs_…` value, not caller-chosen) — worth remembering that "the key looks unguessable" is not itself a substitute for tenant-scoping the index. `convex/schema.ts`, `convex/agentTasks.ts`.
- **`creditLedger.spendCredits`'s idempotency replay now checks the debited amount matches, not just that the key exists.** Also caught in review: `dispatch` reused the caller-supplied `dispatchKey` directly as the credit spend's `idempotencyKey`, in the same key space the public `creditLedger.spend` mutation lets any caller write to. A cheap `spend({amount:1, idempotencyKey:"X"})` followed by `dispatch({dispatchKey:"X", creditCost:100000})` hit the "already a transaction under this key" replay branch and returned the old (much smaller) `balanceAfter` without debiting the difference — the credit gate was bypassable by anyone who could predict or collide with the derived key. Two-part fix: (1) `dispatch` now namespaces its derived key as `` `dispatch:${dispatchKey}` `` instead of the bare `dispatchKey`, so it doesn't share key-space with arbitrary direct `spend` calls by accident; (2) `spendCredits` itself now throws `credit_spend_conflict` if an existing row under the same `(businessId, idempotencyKey)` has a different `amount`, instead of always treating same-key as "safe to replay" — this is the actual fix, since (1) alone only raises the bar to guessing the prefix. `convex/creditLedger.ts`, `convex/agentTasks.ts`.
- **The credit debit's transaction row and event are back-filled with `taskId` after the task is inserted, not left unlinked.** `spendCredits` runs before the task exists (has to — that's the whole point of gating before the effect), so it can't set `taskId` on the write it makes. `dispatch` now patches both the `creditTransactions` row and the `credit_debit` event with the new `taskId` immediately after `ctx.db.insert("agentTasks", …)`, still inside the same mutation/transaction. Without this, `agentEvents.listByTask` couldn't show a task's own credit debit next to its dispatch/status-change events — the only trace was a free-text `reason` string. `convex/agentTasks.ts`.
- **`agentTasks.dispatch` validates `maxAttempts >= 1`; `recordAttemptFailure` now rejects a call against an already circuit-broken task.** A `maxAttempts` of `0` or negative would trip the breaker on the very first recorded failure (or never let a task run at all); rejected with `invalid_max_attempts` before any row is created. Separately, `recordAttemptFailure` previously kept incrementing `attemptCount` on a task that was already `circuitBroken` — harmless in the sense that `advanceStatus` was already blocking it, but it let the row's failure count drift past `maxAttempts` for no reason; it now throws `task_circuit_broken` immediately, the same guard `advanceStatus` already had. `convex/agentTasks.ts`.
- **THI-47 — content templates are render functions with placeholder fallbacks, not static strings, because `businesses` doesn't model owner/offer/audience data yet.** The 8 canonical files need per-business facts (owner name/email, offer, target audience) that have no schema home yet — Phase 1/2 never needed them and `businesses` only carries `name`/`slug`/`ownerUserId`/checkout+payout fields. Rather than inventing schema for this pass (out of scope — this issue is content only) or leaving those sections blank, `convex/lib/agentContextTemplates.ts` takes them as optional render args and falls back to clearly-labeled placeholder copy ("_Not captured yet — ..._") the owner/CEO can fill in later. `OWNER.md` and `BUSINESS.md` lean on this most; `PLATFORM.md`/`RUNBOOK.md`/`CODE_MAP.md` need no business-specific facts at all and render identically for every business.
- **THI-47 — `PLAYBOOK.md` ships one generic default, not MadeThis's per-business-type variants.** `madethis-agent-architecture.md` documents MadeThis seeding `PLAYBOOK.md` from a server-side `playbooks.ts` template library keyed by business type (a stub confirms this exists but the template bodies were never recoverable). ThisMade has no equivalent template library yet — building one is a provisioning-time feature, not a content-writing task. `renderPlaybook()` ships a single reasonable default (first-7-days checklist, weekly rhythm, autonomy boundaries) that applies to any business type; a future provisioning phase can add per-type variants without changing the storage contract.
- **THI-47 — `RUNBOOK.md` and `CODE_MAP.md` are original, not adapted from any captured MadeThis body.** Per `madethis-agent-architecture.md`, both files' bodies were "referenced but not synced" in the HAR capture and are confirmed absent even in the one live business inspected — there was nothing to study the shape of even at a structural level. Both are written directly from this repo's own real implementation instead: `RUNBOOK.md`'s procedures (dispatch a task, credits exhausted, circuit breaker tripped, owner-secret needed) come straight from `agentTasks.ts`'s actual documented behavior above in this file; `CODE_MAP.md` describes this repo's real top-level layout. Lowest IP-boundary risk of the eight by construction — nothing to accidentally echo.
- **THI-47 — the one required skill is `brandkit` (image-generation brand identity kit), matching the existing test literal.** `agentSkills.test.ts` (THI-8) already uses `"brandkit"` as its example `skillKey` in assertions that don't check content — picking the same key for the real skill keeps that consistent instead of introducing an unrelated second key. Content in `renderBrandIdentityKitSkill()` is original: a strategy-note-first structure, 3 logo-concept construction methods, and a fill-in-the-brackets prompt template — same functional idea as MadeThis's captured `01-brandkit.md` (an image-gen skill for brand identity) but roughly 1/6th the length and entirely different wording/section names, scaled to what THIS internal MVP clone actually needs rather than matching MadeThis's ~22KB skill depth.
- **THI-47 — landed via a new `action` (`convex/seedAgentContext.ts`), not a change to the existing mutations.** `agentContextFiles.upsert`/`agentSkills.upsert` (THI-8) are explicitly out of scope for this issue. Convex mutations can't call other mutations (`ctx.runMutation` only exists on `ActionCtx` — the same reason `agentTasks.dispatch` inlines `spendCredits` instead of nesting a `runMutation` call, per the Phase 3 dispatch decision above), so `seedDefaults` is an `action` that calls the two existing public mutations once per file/skill. - **§deploy/§auth (2026-08-27, follow-up to [THI-41](/THI/issues/THI-41)) — Clerk removed entirely; app-level auth replaced by Vercel Authentication (deployment protection) at the platform level.** Clerk's keys were never provisioned — the Marketplace checkout link generated for THI-41 requires a human to accept Clerk's EULA and finish account setup, a one-time consent step nobody had completed, so production ran on Clerk's "keyless" dev-mode fallback and hit `500 MIDDLEWARE_INVOCATION_FAILED` once deployed for real. The only bypass is a shared secret appended to each request (`?x-vercel-protection-bypass=...`), which Stripe's webhook URL can carry (a one-time config change), but which every external `/v1` API consumer would also need to know and send on every call — not workable for a real external API. - **THI-68 — the live worker-execution loop is a new `dispatcher.runTask` action, not a change to `agentTasks.dispatch` itself.** THI-8/THI-62's `dispatch` only ever wrote a row; nothing called it. Considered scheduling the worker run from inside `dispatch`'s own mutation (Convex mutations can call `ctx.scheduler.runAfter` as a transactional side effect) but rejected it: `convex-test`'s scheduler doesn't auto-execute scheduled functions unless a test opts in via `finishAllScheduledFunctions`, so either approach was equally test-safe, but a separate `dispatcher.runTask` action keeps `dispatch` — and its pre-existing 20+ passing tests — completely untouched. `runTask` calls the existing `dispatch` mutation verbatim, then schedules `workerRunner.runWorkerTask`. Idempotent for free: a retried call replays `dispatch`'s own `dispatchKey` dedup, and the scheduled run's first step (`beginWorkerRun`) is a `todo -> in_progress` transition that throws (caught, no-op) if the task already left `todo` — Convex mutation serializability is what actually prevents a double-run, not application-level locking. `convex/dispatcher.ts`, `convex/workerRunner.ts`.
- **THI-68 — identity boundary: `beginWorkerRun`/`completeWorkerRun` take no `actor` parameter at all, rather than trying to validate a caller-supplied one.** The existing `advanceStatus` (THI-62) already required callers to *supply* an `actor`, but supplying one is not the same as proving it — any service-secret holder could call it with `actor: "owner"` and have that accepted and logged. Since there's no real session/identity layer to correlate a caller against yet (Clerk was removed entirely — see the Phase 1 §deploy/§auth entry below — and no replacement exists), THI-68 doesn't try to bolt on a fake one. Instead the worker loop's only two entry points hardcode their actor server-side (`beginWorkerRun` always logs `"system"`, `completeWorkerRun` always logs `"worker"`) and structurally cannot reach `needs_review -> done` at all — that transition stays behind the untouched, owner/ceo-gated `advanceStatus`, unreachable by anything this loop's code can call. A worker driven by injected instructions has no code path to declare itself the owner, because the function it can call doesn't have an actor parameter to lie on. `convex/agentTasks.ts` (`transitionTask` extracted as the shared helper both use).
- **THI-68 — `agentEvents.logWorkerEvent` is deliberately narrower than `logEvent`'s full richContent union.** `actor` is restricted to `"worker"|"system"` and `event` to `tool_call`/`tool_result`/`file_diff`/`error` only — the same identity-boundary reasoning as the status mutations above, applied to the audit trail: the worker loop can log what happened during its own run, never a `chat_message`/`dispatch`/`status_change`/`credit_debit` event or an owner/ceo-attributed anything. `convex/agentEvents.ts`.
- **THI-68 — `marketing` workers never get an E2B sandbox provisioned at all; `coding`/`browser` always do.** THI-66's future tool-allowlist work names "a marketing worker should never reach a raw shell/file-write tool a coding worker needs" as a requirement. Rather than relying purely on a runtime allowlist check to enforce that, marketing's tool set (`read_context_file`, `submit_draft`) has no sandbox-backed tool in it at all, and `workerRunner.ts` skips sandbox creation entirely for that workerType — least privilege enforced by what's architecturally reachable, not just by a policy list that could drift. `convex/workerRunner.ts`, `convex/lib/workerTools.ts`.
- **THI-68 — the tool-allowlist chokepoint ships; the destructive-call approval gate doesn't.** Per the issue's own scope split with THI-66 (filed as a follow-up, blocked on this one): `convex/lib/workerTools.ts`'s `assertToolAllowed` is the enforcement point every tool call passes through, and each workerType's registered tool set is the (minimal, default) allowlist — but a human-approval pause for destructive calls within an already-allowed tool (e.g. a `coding` worker's `run_shell`) is intentionally not built here.
- **THI-68 — worker instructions are read back from the `dispatch` agentEvents row, not stored on `agentTasks` itself.** `agentTasks.dispatch` (THI-8) only ever patched `title`/`description` onto the task row; the actual `instructions` string only ever landed on the `dispatch`-kind event it logs. Rather than adding a schema field to duplicate it (`agentTasks` is exercised by 20+ existing tests and callers), `workerRunner.ts` queries `agentEvents.listByTask` and reads the one `dispatch` event's `instructions` field — dispatch's own idempotency guarantees there's ever exactly one. `convex/workerRunner.ts`.
- **THI-68 — the LLM client is the Vercel AI SDK (`ai` v6) routed through AI Gateway via a plain `"provider/model"` string, not a direct `@anthropic-ai/sdk` dependency.** Matches this build's platform guidance (prefer Gateway model strings; don't default to a provider-specific package). Tools are registered via `jsonSchema()` (no `zod` dependency added) with no `execute` function, so `generateText` returns tool calls without auto-running them — `convex/lib/workerLoop.ts` owns the actual multi-turn loop so every tool call gets its own `tool_call`/`tool_result` event pair, not just a finished sequence. `convex/lib/llmClient.ts`.
- **THI-68 — sandbox/LLM I/O sits behind injected interfaces (`SandboxProvider`, `LlmClient`) so the orchestration loop is unit-testable without live credentials.** Neither `E2B_API_KEY` nor an AI Gateway credential was provisioned in the environment this loop was built in. `convex/lib/workerLoop.ts` has zero imports of `e2b`/`ai`/Convex — `workerLoop.test.ts` exercises turn sequencing, the tool-denial path, and both circuit breakers (turn count, wall-clock) against fakes. `convex/workerRunner.ts` (the one `"use node"` file that wires in the real E2B/AI SDK implementations) was verified two ways: unit tests for everything it delegates to, and a real run against the live dev deployment (`dispatcher:runTask` via `npx convex run`, against a dedicated `thi-68-smoke-test` business) confirming the exact designed failure path end-to-end — `beginWorkerRun` logged `actor: "system"` on the `todo -> in_progress` transition, a missing `E2B_API_KEY`/`AI_GATEWAY_API_KEY` surfaced as a caught error (not a hang or silent failure), and `recordAttemptFailure` correctly tripped `circuitBroken` at `maxAttempts`. - **§deploy ([THI-57](/THI/issues/THI-57)) — `*.storefronts.rough.ink` dedicated as the storefront domain, and no manual wildcard DNS record turned out to be needed.** Resolves the domain-strategy gap left open above: dedicated a subdomain of the company's existing `rough.ink` (not a new domain purchase — free, reversible, no new registrar/DNS zone while the pipeline proves out on one business). `vercel domains inspect rough.ink` confirmed its nameservers are already Vercel's own (`ns1`/`ns2.vercel-dns.com`), so Vercel is authoritative for the whole zone — meaning a manually-provisioned wildcard DNS record for `*.storefronts.rough.ink` isn't necessary and would be actively counter-productive: it would have to point at one single project, contradicting the one-Vercel-project-per-business model. Instead, `vercel domains add {slug}.storefronts.rough.ink {slug}-storefront` (per business, run by the new `scripts/deploy-storefront.mjs`) auto-provisions both the DNS record and the TLS cert against the already-delegated zone — verified live: `acme-test.storefronts.rough.ink` resolved to Vercel's anycast IPs and served a real `200` within ~15s of the domain being added, with zero manual DNS step. `scripts/deploy-storefront.mjs` links the storefront repo to a `{slug}-storefront` Vercel project, runs `vercel deploy --prod`, registers `{slug}.storefronts.rough.ink` (idempotent — already-assigned is not an error), and live-verifies the domain per the THI-41 rule above before reporting success. `scripts/scaffold-storefront.mjs` now calls it as a final step 7 by default (`--skip-deploy` opts out, e.g. for a sandbox with no Vercel CLI session), so `{slug}.storefronts.rough.ink` — not the `{project}.vercel.app` fallback — is the default production domain for every future business. `acme-test` was re-deployed through this exact script and now serves at `https://acme-test.storefronts.rough.ink/` (the old `.vercel.app` alias is left in place alongside it; Vercel adds aliases rather than replacing them, and removing it wasn't asked for).
