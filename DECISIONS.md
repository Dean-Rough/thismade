# Decisions

Running log of assumptions made where `docs/` was silent, per `PAPERCLIP-GOAL.md` §Budget & stop rules.

## Phase 1: Foundation ([THI-6](/THI/issues/THI-6))

- **Success envelope shape.** The docs only specify the error envelope (`madethis-rebuild-plan.md` §3). The issue names the success envelope fields (`data`, `hint`, `next_action`) but not their types. Assumption: `hint` and `next_action` are nullable strings (`string | null`), defaulting to `null` when a handler has nothing to add. `lib/api/envelope.ts`.
- **`/v1` mount point.** MadeThis serves `/v1` from a separate `api.madethis.com` host. For this self-hosted clone we mount `/v1/*` inside the same Next.js app (`app/v1/**/route.ts`) rather than standing up a second service — simplest choice that satisfies "GET /v1/business" literally, revisit if Phase 6's public developer platform needs host separation.
- **API key format.** Never reuse MadeThis's `mt_live_...` prefix (naming constraint). Using `tm_<test|live>_<48-hex>`; only `test` mode keys are minted anywhere in this build per the no-live-spend constraint. `convex/lib/apiKeyCrypto.ts`.
- **`docs_url` base.** No public docs site exists yet for this internal clone. Using a placeholder `https://docs.thismade.internal/api/errors#{code}` — update once a real docs host exists.
- **Idempotency-Key scope.** Doc only says keys are 1-128 ASCII chars and replay results. Assumption: a key is scoped per `(businessId, route)`, not global, so two different businesses (or two different endpoints) can reuse the same key string independently. Enforced via the `idempotencyKeys.by_business_route_key` index.
- **Idempotency conflict semantics.** `idempotency_conflict` (409) is returned both for (a) the same key reused with a different request body, and (b) a concurrent request while the original is still `in_progress` — matches the doc's description "Concurrent request with identical idempotency key" plus the general idempotency-key contract (same key ⇒ same body). The check-and-claim is one atomic Convex mutation (`idempotencyKeys.beginOrReplay`) specifically to avoid a race between two concurrent first-attempts.
- **Mutation endpoint used to exercise idempotency.** Phase 1's issue scope names only `GET /v1/business`. The gate requires the Idempotency-Key middleware to be "exercised with a duplicate-request test," which needs a mutation endpoint. Added `PATCH /v1/business` (updates `checkoutReturnUrl` only) — it's already in the doc's endpoint inventory (`madethis-rebuild-plan.md` §3 table) right next to `GET /v1/business`, so this stays inside the documented Business API surface rather than inventing a new one.
- **Cross-tenant 404 proof surface.** `GET/PATCH /v1/business` resolve the business from the caller's own API key (no id parameter), so there's no direct cross-tenant probing surface on that endpoint by construction. The tenancy contract itself — "fetching a document belonging to another business behaves exactly like it doesn't exist" — is implemented once as a shared helper (`convex/lib/tenancy.ts`) and proven against `apiKeys` (the one other Phase-1 table with per-row `businessId`), since every later phase's id-scoped resources (products, orders, etc.) will route through the same helper. See `convex/tenancy.test.ts`.
- **Convex codegen ran offline.** This build environment has no network access to authenticate a Convex deployment, so `npx convex dev`/`codegen` can't run. `convex/_generated/{dataModel,server,api}.ts` were hand-written to match the CLI's own templates (verified against `node_modules/convex/src/cli/codegen_templates/*.ts`), with `api.ts` backed by Convex's documented codegen-free fallback (`anyApi`). Regenerate for real once a Convex deployment exists — the hand-written files should be byte-for-byte replaceable by `npx convex dev` output for this schema.
- **Clerk scope for Phase 1.** Only wired the multi-tenant session boundary (`ClerkProvider`, `clerkMiddleware`, `/v1/*` excluded from session auth since it uses Bearer API keys instead). Business-switching UI itself is dashboard UX, out of scope for the Foundation gate — tracked as follow-up, not blocking.
- **§frontend ([THI-15](/THI/issues/THI-15)) — design-token spike.** Part 8 open question 2 of the accepted [THI-14](/THI/issues/THI-14) plan asked for a short, concrete color/type pass before Phase 1 UI work rather than picking final values ad hoc. Landed as `lib/design-tokens.ts` (source of truth, referenced by `tailwind.config.ts` and mirrored as CSS variables in `app/globals.css`): a warm off-white surface + warm near-black ink (not MadeThis's cream/charcoal), a terracotta accent (deliberately not a generic SaaS blue), and separate confirmation-state vs credit-usage semantic color scales per Part 2.2 (same hues today, free to diverge later without a rename). Typography: Manrope (sans, UI/body), Fraunces (serif, used sparingly — only the marketing headline and empty-states, never dense dashboard UI), IBM Plex Mono (mono, technical surfaces) — all three deliberately distinct from MadeThis's verified pairing (Inter / Instrument Serif & Inria Serif / Geist Mono). These are easy to tune later since every surface reads from the token file; flagging for a design sanity-check rather than blocking on approval before shipping, per the plan's "for review" framing.
- **§frontend ([THI-15](/THI/issues/THI-15)) — shadcn/ui installed by hand, not via `npx shadcn add`.** The current shadcn CLI (v4.19.0, "Nova" preset) defaults to Tailwind v4 syntax (`@theme`, `@utility`, oklch colors in `app/globals.css`), which Tailwind v3.4 (this repo's version, kept deliberately per THI-14 Part 2.3: "revisit v4 migration only after Phase 1 ships, as a separate, isolated upgrade") cannot parse. Ran `shadcn init`, saw the v4 output, reverted it, and hand-built the classic v3-compatible shadcn pattern instead: CSS-variable colors in `app/globals.css` (`:root`/`.dark`), `tailwind.config.ts` mapping color names onto those variables, `class-variance-authority` + `radix-ui`'s `Slot` for `components/ui/button.tsx`, `tailwindcss-animate` as the v3 plugin. `components.json` is still present for editor/tooling recognition, but running `npx shadcn add <component>` against this repo will likely re-inject v4 syntax — review its output against `app/globals.css` before accepting rather than taking it as-is.
- **§frontend ([THI-15](/THI/issues/THI-15)) — Clerk keyless dev mode, no real keys yet.** No Clerk account/publishable+secret keys are provisioned for this project (`GET /api/agents/me/secrets` returns none, `.env.example` has them blank). `next dev` uses Clerk's own "keyless" auto-provisioning to run without configuration — confirmed `/sign-in`, `/sign-up`, and the dashboard shell all render correctly this way. `next build` has no such fallback: `ClerkProvider` throws `Missing publishableKey` while prerendering any route once it wraps real Clerk-consuming components (this never surfaced before THI-15 because `app/page.tsx` was static boilerplate that never exercised Clerk). Fixed by making the whole app dynamically rendered (`export const dynamic = "force-dynamic"` in `app/layout.tsx`) rather than papering over it with fake keys — an app whose every route sits under `ClerkProvider` gets little from static optimization anyway. Revisit per-route static rendering once real keys exist. Needs a real Clerk account before this can ship past internal use — flagged to Mad Jimmy, same class of gap as the Convex codegen note above.
- **§frontend ([THI-15](/THI/issues/THI-15)) — `auth.protect()` redirects to our own `/sign-in`.** By default `clerkMiddleware`'s `auth.protect()` redirects unauthenticated requests to Clerk's hosted account portal, not this app's own pages. Since THI-15 ships custom `/sign-in`/`/sign-up` routes, `middleware.ts` now passes `unauthenticatedUrl` explicitly (building a `/sign-in?redirect_url=...` URL) so the redirect stays on `thismade` and returns the user to the page they requested after signing in.
- **§frontend ([THI-15](/THI/issues/THI-15)) — single implicit business context.** Per this file's Phase 1 Clerk-scope note above and THI-14 Part 8 open question 5, the dashboard nav rail shows a static "Your business" label instead of a switcher — `/dashboard/businesses` and real multi-business state remain a later-phase follow-up, not built here.

## Phase 2: Commerce MVP ([THI-7](/THI/issues/THI-7))

- **§products — Stripe sync uses raw `fetch`, not the `stripe` npm SDK.** [THI-24](/THI/issues/THI-24) only needs two calls (create Product, create Price). Hand-rolling them against Stripe's REST API (`lib/stripe/products.ts`) keeps the dependency footprint at zero and makes the sync trivially mockable at the `fetch` boundary in tests, matching how `app/v1/business/route.test.ts` mocks the Convex wire boundary rather than the route's own logic. Revisit if a later phase (webhooks, Connect payouts) needs enough Stripe surface that the SDK's typed request/response shapes start paying for themselves.
- **§products — Stripe sync ordering.** Convex mutations can't make outbound HTTP calls, so the REST layer (`PATCH /v1/products/{id}`) calls Stripe *before* calling `products.update`, only when the request transitions `status` to `"active"` from something else. This means a Stripe failure returns `internal` without touching the row at all — never a product marked `"active"` with missing `stripeProductId`/`stripePriceId`. `products.update` accepts the resulting ids as plain optional args rather than reaching out to Stripe itself.
- **§products — test-mode key enforced at the sync boundary.** `lib/stripe/products.ts` throws unless `STRIPE_SECRET_KEY` starts with `sk_test_`, so a live key pasted into env by mistake fails loudly instead of silently placing a real charge-eligible Product/Price. Matches the build-wide "Stripe test-mode only, no live keys" constraint.
- **§products — Idempotency-Key route scope on parameterized paths.** `PATCH /v1/products/{id}` scopes its idempotency record to the literal route template `"PATCH /v1/products/:id"` (not the concrete id), consistent with the existing `(businessId, route)` scoping decision above — an Idempotency-Key is a client-chosen nonce for one logical operation, not automatically namespaced per resource.
- **§files — tenancy anchor is `fileId`, not the raw Convex `storageId`.** [THI-27](/THI/issues/THI-27)'s ticket text frames the check as "`files/complete` verifies the caller's businessId matches the storageId's owner," but that's not literally possible: Convex's `storageId` doesn't exist until the caller finishes PUTting bytes to the signed `generateUploadUrl()` URL, which happens *after* `POST /v1/files` returns and entirely outside our REST layer (a direct HTTP call to Convex). So `POST /v1/files` (`files.createPendingUpload`) inserts a `files` row — `{businessId, status: "pending", storageId: undefined, createdAt}` — before any bytes move, and returns its id as `fileId` alongside the upload URL. `fileId` (handed only to the business that requested it) is the real tenancy anchor: `POST /v1/files/complete` runs `fileId` through the standard `convex/lib/tenancy.ts` `getScoped` helper against the caller's `businessId` before it will attach the now-known `storageId` and flip `status` to `"complete"`. A cross-tenant `fileId` is indistinguishable from a nonexistent one (`getScoped` → `null` → REST `not_found` 404), matching the build-wide "404 never 403" contract. See `convex/files.ts`, `convex/files.test.ts`.
- **§files — both endpoints require `Idempotency-Key`.** The ticket's endpoint table doesn't tag `POST /v1/files` / `POST /v1/files/complete` with "(Idempotency required)" the way it does for refunds, but `madethis-rebuild-plan.md` §3's general rule ("Mutation endpoints require an `Idempotency-Key` header") applies to every state-changing `/v1` route, not just the annotated ones — consistent with how `PATCH /v1/business` and `POST /v1/products` already work. Both file routes go through the existing `lib/api/idempotency.ts` `withIdempotency` wrapper unchanged.
- **§files — permanent URL is `ctx.storage.getUrl(storageId)`, not a hand-built `/api/storage/{uuid}` string.** `madethis-convex-api-reference.md` documents retrieval as `GET https://<deployment>.convex.cloud/api/storage/{uuid}`, but Convex's own SDK exposes `ctx.storage.getUrl()` specifically so callers never hand-construct that path (the exact URL shape is a Convex implementation detail, e.g. it may carry a token). Using the SDK method keeps `files.completeUpload` correct if that internal format changes, and it's what `convex/files.test.ts` proves is actually fetchable (round-trips a real stored blob).
- **§payouts — Connect calls stay on raw `fetch` too, no `stripe` npm SDK.** [THI-28](/THI/issues/THI-28)'s ticket text flagged Connect payouts as the point where the SDK's typed shapes might start paying for themselves (see the §products decision above). In practice the surface is still just two calls (create Express account, create an Account Link) plus local webhook-signature verification, so `lib/stripe/connect.ts` follows the exact same hand-rolled-`fetch` + `sk_test_`-only-key shape as `lib/stripe/products.ts`, rather than mixing two different Stripe client styles in one repo. Revisit only if a later phase needs enough additional Stripe surface (e.g. full Checkout Session objects) that re-parsing responses by hand becomes the bottleneck.
- **§payouts — webhook signature verification is hand-rolled HMAC, not `stripe.webhooks.constructEvent`.** Without the SDK, `lib/stripe/webhook.ts` reimplements Stripe's documented manual verification (https://stripe.com/docs/webhooks#verify-manually) with Web Crypto (`crypto.subtle`), including the same 300s replay-tolerance window the SDK defaults to. No outbound network call is involved, so this is deterministic and fully unit-tested (`lib/stripe/webhook.test.ts`) without touching Stripe's API.
- **§payouts — one webhook handler file for all inbound Stripe events.** `app/api/webhooks/stripe/route.ts` is intentionally not under `/v1/*`: it's Stripe calling us, not an API-key-authenticated platform client, so it skips the `{data,hint,next_action}`/`{error}` envelope entirely (signature verification stands in for auth; Stripe only reads the HTTP status). It currently switches on `event.type` with only `account.updated` handled — the Checkout ticket's webhook should extend the same switch rather than standing up a second Stripe webhook endpoint, since Stripe's own dashboard/CLI configuration is simplest with exactly one endpoint URL per environment.
- **§payouts — Connect account id is set once, never swapped.** `payouts.setStripeConnectAccountId` is a no-op if the business already has a `stripeConnectAccountId`; a retried `onboarding-link` call reuses the existing account and just mints a fresh Account Link (they expire in minutes). This also protects the `account.updated` webhook's lookup index (`businesses.by_stripe_connect_account_id`) from ever needing to handle a business's account id changing out from under it.
- **§payouts — `GET /v1/payouts` requires the `money` scope even though it's read-only.** The endpoint table (`madethis-rebuild-plan.md` §3) explicitly tags both payouts routes `apiKey (money)`, unlike `GET /v1/business` which requires no scope — payout eligibility is treated as sensitive financial data, not general business metadata, so the stricter tag is followed literally rather than assuming GETs are always scope-free.
- **§payouts — platform base URL for onboarding-link redirects.** Account Links require absolute `refresh_url`/`return_url`s Stripe redirects the browser to after hosted onboarding. No such base URL existed yet (Phase 1's `checkoutReturnUrl` is a per-business, caller-supplied value, not the platform's own origin), so a new `NEXT_PUBLIC_APP_URL` env var was added (`.env.example`) rather than overloading `checkoutReturnUrl` for an unrelated purpose.
- **§orders — `status` tracks paid/refunded only; shipped is a separate optional field.** [THI-25](/THI/issues/THI-25)'s ticket text flags this explicitly: `madethis-rebuild-plan.md`'s sketch has a single mutually-exclusive `status` union (implicitly `paid | refunded | shipped`), but a real order can be shipped *and later* refunded — that union can't express both facts at once. `orders.status` is `"paid" | "refunded"`; `shippedAt`/`shippingTrackingCode` and `refundedAt` are independent optional fields set by the (follow-up) Orders API ticket's ship/refund mutations. `convex/schema.ts`.
- **§orders — idempotent order creation is a check-then-insert on `by_stripe_session`, not a second idempotency-key table.** Stripe redelivers `checkout.session.completed` on retry or manual resend. Rather than routing the webhook through `lib/api/idempotency.ts` (built for `Idempotency-Key`-bearing REST requests, not inbound Stripe events), `orders.createFromCheckoutSession` mirrors `idempotencyKeys.beginOrReplay`'s own pattern directly: query `by_stripe_session` for an existing row and only insert if none exists, all inside one Convex mutation so two concurrent deliveries can't both observe "no existing row." `convex/orders.ts`.
- **§orders — the webhook resolves `businessId`/`productId` from Checkout Session `metadata`, not a Stripe price → product lookup.** `POST /v1/checkout-links` sets `metadata[businessId]` / `metadata[productId]` when creating the session (`lib/stripe/checkout.ts`); the webhook reads them straight off the completed session object. This avoids needing a `stripePriceId → product` reverse index and keeps `checkout.session.completed` handling a single Convex mutation call with no extra queries. A session missing that metadata (or missing amount/currency/email) is acknowledged (200) but not turned into an order — it can never have come from our own `/v1/checkout-links`, so retries would never succeed either. `app/api/webhooks/stripe/route.ts`.
- **§orders — checkout-links reuses the raw-`fetch` Stripe style, and `POST /checkout/sessions` mode is `payment`.** Follows the same hand-rolled-`fetch` + `sk_test_`-only-key shape as `lib/stripe/products.ts`/`lib/stripe/connect.ts` (see the §products/§payouts decisions above) — one Checkout Session call, `mode: "payment"` (one-time purchase, matching the doc's "customer checkout sessions" for products, not subscriptions). `lib/stripe/checkout.ts`.
- **§orders — checkout-links requires `businesses.checkoutReturnUrl` to already be set.** The ticket says success/cancel URLs "derive from `businesses.checkoutReturnUrl`," but doesn't say what happens if it's unset. Rather than falling back to some platform default (there isn't one — unlike payouts' `NEXT_PUBLIC_APP_URL`, this is meant to redirect back to the *business's own* storefront), `POST /v1/checkout-links` rejects with `validation_failed` until the business configures it via the existing `PATCH /v1/business`. `app/v1/checkout-links/route.ts`.
- **§orders (Orders API, [THI-26](/THI/issues/THI-26)) — `refund_already_issued` is a new `ErrorCode` literal, not a reuse of `validation_failed`.** The ticket flags this explicitly as undecided by either doc. Refunding an already-refunded order is a state conflict on an existing resource, the same shape as `idempotency_conflict` (both mean "this exact operation cannot run again against this identity"), not a malformed-request problem — `validation_failed` is reserved for bad input shape elsewhere in this codebase (missing fields, wrong types, unparseable JSON). Added as its own literal mapped to `409 Conflict`, matching `idempotency_conflict`'s status code. `lib/api/envelope.ts`.
- **§orders — shipping a refunded order is allowed, not a hard error.** The schema comment on `orders.status` (`convex/schema.ts`, from [THI-25](/THI/issues/THI-25)) already establishes `shippedAt`/`refundedAt` as independent facts because a shipped order can later be refunded; the converse (refunding, then still shipping — e.g. a refund processed as a goodwill gesture before the fulfillment queue caught up) is equally valid business behavior and the schema places no ordering constraint between the two. `POST /v1/orders/{id}/ship` only rejects a *double*-ship (`shippedAt` already set); it does not check `status`. Symmetrically, `POST /v1/orders/{id}/refund` only rejects a double-refund and doesn't check `shippedAt`.
- **§orders — double-ship reuses `validation_failed` rather than a new error code.** Unlike the refund case, the ticket didn't flag double-ship as needing a dedicated code, and "this order already has a shipment recorded" reads naturally as a request-state validation problem against the current resource rather than an idempotency-style conflict on money already moved — reusing `validation_failed` (400) avoids growing `ErrorCode` for every possible double-mutation instead of just the one the ticket called out.
- **§orders — `POST /v1/orders/{id}/ship` also requires `Idempotency-Key`**, even though only the refund route's ticket text says so explicitly. Same general-rule reasoning as the §files idempotency decision above: every state-changing `/v1` route goes through `lib/api/idempotency.ts`, not just the ones a ticket happens to call out.
- **§gate ([THI-29](/THI/issues/THI-29)) — the live smoke test is a separate, non-hermetic vitest project, not part of `npm test`.** THI-29 asks for an automated test proving DoD item 4 by driving a real Stripe test-mode purchase, "so it runs unattended as part of `npx vitest run` (or a clearly-documented adjacent script if Stripe's flow doesn't fit vitest's model)." A real purchase against Stripe's hosted Checkout page has no server-side "complete this session" API call — Stripe's own documented pattern for testing it is a headless browser filling the real page with the official test card (`4242 4242 4242 4242`). That, plus needing a real deployed Convex backend and a running app instance, makes it fundamentally non-hermetic and credential-dependent, unlike every other test in this repo. Rather than weakening the default suite's zero-credential guarantee, it's split into its own `smoke/commerce-e2e.test.ts` + `vitest.e2e.config.ts` + `npm run test:e2e`, excluded from `vitest.config.ts`'s default include. See `smoke/README.md` for the full runbook.
- **§gate — the live smoke test fails loudly, never silently skips, when credentials are missing.** Matches `PAPERCLIP-GOAL.md`'s "do not fake a pass or stub past the definition of done silently." Each required env var (`NEXT_PUBLIC_CONVEX_URL`, `SMOKE_API_BASE_URL`, `STRIPE_SECRET_KEY`) is checked at module load via a `requireEnv` helper that throws a descriptive error naming exactly what's missing and pointing at `smoke/README.md`, rather than using vitest's `.skip`/`.todo` (which would report green in a CI summary that only checks exit codes).
- **§gate — Playwright is a required *runtime* dependency of the live smoke test only, deliberately not added to `package.json`.** This build's sandbox at the time THI-29 was picked up has no Stripe test-mode credentials or live Convex deployment available (see the `project-convex-codegen-gap` memory), so the live test cannot actually be executed yet — see the THI-29 gate comment thread for the credential blocker. Adding a ~300MB browser-automation devDependency (plus running `npm install`, which would also fold a concurrently-in-flight agent's uncommitted frontend dependency additions into the lockfile) purely so a test that can't run anyway would "import cleanly" wasn't worth the footprint or the coordination risk. Instead `completeHostedCheckout()` in `smoke/commerce-e2e.test.ts` imports `"playwright"` via a *computed* (non-literal) dynamic `import()` specifier — TypeScript treats a non-literal `import()` argument as `any` and skips module resolution for it, so `npm run typecheck` stays green with zero `playwright` install, and the smoke test still throws a clear, actionable error at run time if it's missing. Once the live test is actually runnable, add `playwright` as a real devDependency and switch to a static import.
- **§orders — refund resolves the PaymentIntent via a live Stripe lookup, not a stored field.** `orders` only persists `stripeCheckoutSessionId` (set by the webhook at order-creation time — see the `createFromCheckoutSession` decision above); it never stores a PaymentIntent id. `lib/stripe/refunds.ts` re-fetches the Checkout Session from Stripe (`GET /v1/checkout_sessions/{id}`) to read `payment_intent`, then calls `POST /v1/refunds` against it — two calls instead of one, but it avoids adding a PaymentIntent column purely to serve a refund path that already has everything it needs one Stripe round-trip away. Follows the same raw-`fetch` + `sk_test_`-only-key shape as the other `lib/stripe/*.ts` files.
